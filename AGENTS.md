# TESTAR Trace Development Instructions

Read [README.md](README.md) for the project purpose and repository structure. This file defines how AI agents should modify and validate the repository.

## Architecture Boundaries

- `packages/core` contains the canonical domain models, traceability methods, and analysis logic. Its distribution is `testar-trace`, imported as `testar_trace`.
- `packages/adapters` converts external requirement formats and TESTAR-generated state models into core models. Its distribution is `testar-trace-adapters`, imported as `testar_trace_adapters`.
- `apps` contains runnable interfaces and services. Keep reusable domain and analysis logic in packages.
- `benchmarks` contains curated SUT-specific requirements, TESTAR protocols and settings, and generated state models used as reproducible inputs and examples.
- `docs` contains architecture, domain, planning, and project documentation.

Dependency direction:

```text
apps ────────> adapters ────────> core
  └─────────────────────────────> core
```

Do not introduce reverse dependencies.

## Terminology and Naming

Use naming consistently across source code, metadata, documentation, and user interfaces:

- Use **TESTAR Trace** for the project and product.
- Use `testar-trace` and `testar-trace-adapters` for Python distribution names.
- Use `testar_trace` and `testar_trace_adapters` for Python import packages.
- Use **benchmark** for a curated collection of artifacts associated with one SUT.
- Use **state model** as a noun and **state-model** as a compound modifier.
- Use **trace link**, **traceability method**, and **traceability result** consistently.
- Use **requirements completeness** for the primary evaluated property. Treat
  coverage as a supporting diagnostic, never as an equal product objective.
- Do not reintroduce the legacy names `ReqTrace` or `reqtrace`.

## Development Rules

- Default to deterministic and reproducible traceability methods.
- Add AI- or machine-learning-based traceability methods only when explicitly requested. This does not prohibit random or AI-driven TESTAR protocols stored as benchmark inputs.
- Put canonical models, traceability methods, and analysis logic in `core`.
- Put format- and source-specific parsing and conversion in `adapters`.
- Keep applications thin and move reusable functionality into packages.
- Prefer small modules named after their responsibility over generic modules such as `utils`, `helpers`, or `common`.
- Follow existing patterns before introducing new abstractions.
- Keep changes limited to the requested scope.
- When renaming packages or modules, update imports, metadata, documentation, tests, and tooling configuration together.
- Treat public API changes as deliberate. Do not introduce breaking changes incidentally.
- Add or update tests for behaviour changes.
- Update documentation when public behaviour, commands, formats, terminology, or architecture change.
- Regenerate generated files with their owning tools; never edit them manually.

## Benchmark Artifacts

Treat versioned artifacts under `benchmarks` as reproducible inputs unless explicitly requested otherwise. These may include:

- requirements in supported external formats;
- TESTAR protocols and settings;
- state models generated by TESTAR;
- manually prepared reference data;
- expected traceability results used for evaluation.

Although state models are generated by TESTAR, committed benchmark state models are inputs to TESTAR Trace and should not be changed incidentally.

- Keep outputs generated by TESTAR Trace separate from benchmark inputs unless an output is intentionally promoted to a versioned reference result.
- Use small, focused fixtures for unit tests. Use complete benchmarks only for integration, regression, or evaluation tests.
- Preserve stable identifiers, file relationships, and deterministic ordering.
- Set and document random seeds when randomness is unavoidable.
- Do not commit secrets, credentials, personal data, or machine-specific paths.

## Configuration and Dependencies

Configuration files may be edited when required by the task. Mechanical changes that preserve existing policy do not require separate approval.

- Never weaken validation or add exclusions merely to make checks pass.
- Update `uv.lock` with uv when project metadata, dependencies, or workspace membership change.
- Never edit `uv.lock` manually.
- Do not delete `uv.lock` or perform broad dependency upgrades unless explicitly requested.
- Use the tools and package managers configured by the repository.
- Keep this file concise and repository-specific.

Only make the following changes when the task explicitly includes them:

- Change supported Python versions.
- Replace development tools or build systems.
- Add, remove, or upgrade dependencies.
- Add or remove workspace members.
- Change package boundaries, schemas, or interchange formats.
- Make breaking public API changes.
- Weaken linting, typing, testing, or coverage policy.
- Change CI, release, publishing, or deployment configuration.
- Change licensing, attribution, citation metadata, or this file.

## Working Process

Before making changes:

1. Inspect the relevant source, tests, configuration, and documentation.
2. Identify the affected package, application, or benchmark.
3. Create a short plan for non-trivial changes.
4. Keep the implementation focused on the requested task.

## Validation

Run the applicable checks from the repository root:

- `uv sync --all-packages --all-groups --locked`
- `uv format --check`
- `uv run ruff check .`
- `uv check --all-packages`
- `uv run ty check`
- `uv run pytest --cov --cov-report=term-missing -q`

When package metadata or distribution contents change, also run:

- `uv build --all-packages`

When dependencies change, also run:

- `uv audit`

For web changes, follow [apps/web/AGENTS.md](apps/web/AGENTS.md) and run the relevant check, coverage, build, bundle-budget, and browser-test scripts declared in `apps/web/package.json` using its configured package manager.

Run targeted checks during development and the broadest practical checks before completion. If a check cannot be run or fails for a pre-existing reason, report that clearly.

## Version Control

- Do not commit, push, merge, tag, release, or publish unless explicitly requested.
- When asked to commit, use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) and keep commits focused.
- Review the complete diff before committing or reporting completion.
- Do not rewrite history or discard unrelated changes.
