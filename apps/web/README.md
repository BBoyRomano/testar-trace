# TESTAR Trace Web

`testar-trace-web` is the client-side web application for requirements traceability in state models generated by [TESTAR](https://testar.org/).

## Scope

The application provides browser-based workflows for:

- importing requirements, TESTAR-generated state models, and analysis configuration;
- combining multiple requirement artifacts into one requirement set and multiple state-model
  artifacts into one collection;
- reviewing how requirement and state-model sources were parsed before running an analysis;
- selecting and configuring a traceability method;
- running traceability analysis locally;
- storing and inspecting analysis history;
- importing and exporting history and traceability results;
- inspecting completeness and supporting trace diagnostics per requirement, authored flow,
  branch, and requirement path;
- visualizing complete requirement-path routes while distinguishing direct state, widget,
  action, and transition evidence from connector transitions.

## Application Boundary

The web application contains the user interface, browser persistence, visualization, and browser-specific workflow orchestration.

It does not define canonical domain models, implement traceability methods, or contain format-specific parsing logic. External formats are handled by `testar-trace-adapters`. Domain models, traceability methods, and analysis logic are provided by `testar-trace`.

The Python packages run locally in a Web Worker through Pyodide:

```text
web interface -> Pyodide worker -> adapters -> core
```

Application processing and persistence remain client-side.

## Local Data

Imported files, configuration, history, and results remain in the browser. Completed results are
stored in IndexedDB and can be explicitly imported or exported. The default
`.testar-analysis.json` export is a version 2 portable analysis bundle containing the result,
normalized requirement and state-model snapshots, and the original loaded source text. A
recipient can therefore inspect the same requirements, graphs, and highlighted evidence without
the original files or another analysis run. Import accepts this portable format only, so every
imported analysis retains the context needed for inspection and re-export.

Selecting multiple analyses exports one `.testar-analyses.json` collection. The collection embeds
the same portable version 2 bundle for every selected analysis and can be imported in one step.

## Development

From `apps/web`:

```text
vp install
vp run dev
```

Run validation:

```text
vp check
vp run test
vp run test:coverage
vp exec playwright install chromium firefox webkit
vp run test:e2e
vp run build
vp run check:bundle
```

The unit suite covers pure mapping, filtering, routing, persistence metadata, file handling,
worker protocols, and feature rendering. The cross-browser end-to-end suite uses real benchmark
sources to verify parsing, source review, local analysis, IndexedDB restoration, export/import,
responsive layout, direct routes, failure feedback, and automated WCAG checks. Automated
accessibility checks supplement rather than replace keyboard and screen-reader review.

The application uses client-side routes under `/analyses`. Production hosts must serve
`index.html` for unknown application paths so direct links and page refreshes reach the router.

## Production hosting

TESTAR Trace is a static, client-side application. A production host must:

- use HTTPS and route application navigation requests to `index.html`;
- serve JavaScript modules, web workers, JSON, WASM, wheels, and ZIP files with valid MIME types;
- compress text assets with Brotli or gzip;
- cache hashed assets immutably while keeping `index.html` short-lived;
- keep the versioned files under `python/` cacheable without making an old `index.html` reference
  unavailable runtime assets;
- avoid injecting third-party scripts or making external requests, preserving the local-only data
  boundary.

A compatible Content Security Policy starts with:

```text
default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self' blob:;
connect-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:;
object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'
```

Inline styles are currently required for bounded progress values and graph path colors. Verify the
policy against the deployed Pyodide and worker assets before enforcing it. Also send
`X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. Cross-origin isolation should
only be enabled if a measured feature requires it.

The production build enforces conservative gzip budgets for the application JavaScript, CSS, and
graph chunk, plus a raw-size budget for the lazy Python runtime. End-to-end tests run against the
production preview in Chromium, Firefox, and WebKit. Failed CI runs retain Playwright traces,
screenshots, and the HTML report for diagnosis.

Cloudflare Workers Static Assets is configured in `wrangler.jsonc`. After the
production build is current, validate and deploy it with:

```text
vp run deploy:check
vp run deploy
```

Deployment uploads only `dist/`; no Worker script or server-side storage is
present. GitHub deployment requirements and activation steps are recorded in
[`../../docs/operations.md`](../../docs/operations.md).

Before a release, manually verify keyboard navigation, modal focus return, 200% and 400% zoom,
forced-colors mode, reduced motion, touch input, and a screen reader on the primary creation,
import, and result flows. Automated accessibility checks are a regression guard, not a substitute
for this manual review.
